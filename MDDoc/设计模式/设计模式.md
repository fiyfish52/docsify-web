 ## 责任链模式（Chain of Responsibility Pattern）



`责任链模式（Chain of Responsibility Pattern）`是一种行为设计模式，它允许对象以链式结构处理请求。在这种模式中，通常每个处理器都有一个后继者，处理器会对请求进行处理，如果它能处理该请求，就处理之；如果不能处理，就将请求传递给后继者，直到找到一个能够处理该请求的处理器或者直到链的末端。



### 责任链模式的主要组成部分

**Handler（处理器接口）**：定义了一个处理请求的接口，通常包括一个设置后继者的方法和一个处理请求的方法。
**ConcreteHandler（具体处理器）**：实现了处理器接口，负责处理它所负责的请求，如果不能处理，则将请求传递给后继者。
**Client（客户端）**：创建并配置处理器链，并发起请求。

责任链模式可以将请求发送者与接收者解耦，避免请求发送者与接收者之间的耦合。该模式中，请求沿着责任链依次传递，直到有一个对象处理请求为止。责任链模式的核心是定义责任链节点的接口以及节点之间的关系，它允许动态的增加和修改责任链中的节点。



###  **使用场景**

适用于需要动态地处理请求，并且希望将请求发送者和接收者解耦的场景，例如日志记录、异常处理、权限验证等

### **代码示例**



#### 定义处理器接

```java
public abstract class Handler {
    protected Handler successor;

    public void setSuccessor(Handler successor) {
        this.successor = successor;
    }

    public abstract void handleRequest(int request);
}

```

#### 实现具体处理器

```java
public class ConcreteHandler1 extends Handler {
    @Override
    public void handleRequest(int request) {
        if (request >= 0 && request < 10) {
            System.out.println("ConcreteHandler1 handled request " + request);
        } else if (successor != null) {
            successor.handleRequest(request);
        }
    }
}

public class ConcreteHandler2 extends Handler {
    @Override
    public void handleRequest(int request) {
        if (request >= 10 && request < 20) {
            System.out.println("ConcreteHandler2 handled request " + request);
        } else if (successor != null) {
            successor.handleRequest(request);
        }
    }
}

```

#### 使用责任链

```java
public class ChainOfResponsibilityDemo {
    public static void main(String[] args) {
        // 创建处理器链
        Handler handler1 = new ConcreteHandler1();
        Handler handler2 = new ConcreteHandler2();
        handler1.setSuccessor(handler2);

        // 发起请求
        int[] requests = {2, 5, 14, 22, 18, 3, 17};
        for (int request : requests) {
            handler1.handleRequest(request);
        }
    }
}

```



在上述代码中，Handler 是处理器接口，`ConcreteHandler1` 和 `ConcreteHandler2` 是具体处理器。客户端代码创建了处理器链，并发起了一系列请求。每个请求会按照处理器链的顺序被处理，直到找到能够处理该请求的处理器。

责任链模式使得请求的处理者可以在运行时动态确定，增加了系统的灵活性。但是，也需要注意责任链模式可能带来的性能问题和调试困难。

### **实际应用**



以下是一些常用框架和工具，它们都采用了责任链模式：

1. Spring框架中的拦截器：拦截器是Spring框架中的一种常见组件，它可以在请求处理前后进行一些额外的处理，例如身份验证、日志记录、权限控制等。拦截器就是利用了责任链模式来将多个处理对象构成一条拦截器链，然后逐个处理请求。Spring框架提供了很多拦截器，例如`HandlerInterceptor`、`WebRequestInterceptor`等。
2. Servlet中的过滤器：Servlet中的过滤器也是一种常见的使用责任链模式的场景。过滤器可以在请求处理前后进行一些额外的处理，例如安全认证、数据预处理、异常处理等。
3. Java 8中的Lambda表达式：Java 8中的Lambda表达式可以看作是一种函数式接口，它利用责任链模式来组合、封装和传递函数对象。Lambda表达式可以通过链式结构形成一个函数的序列，然后按顺序逐个执行这些函数并返回结果，从而可以在Java中实现[函数式编程](https://zhida.zhihu.com/search?content_id=231644527&content_type=Article&match_order=1&q=函数式编程&zhida_source=entity)。
4. Netty中的处理器Pipeline：Netty是一种基于事件驱动的网络通信框架，它利用责任链模式和事件监听机制来处理请求。Netty中的处理器Pipeline是一条处理请求的链，该链中的每个处理器都可以对请求进行处理和传递，从而形成一个完整的事件处理流程。

### 优缺点

#### 优点

**解耦**：请求发送者和接收者解耦，发送者不需要知道哪个对象会处理请求。

**灵活性**：可以动态地添加或删除处理器，或者改变处理器的顺序。

**简化对象**：每个处理器只需要关注自己能处理的请求，不需要了解整个请求处理流程。



#### 缺点



**性能问题**：请求可能需要经过多个处理器才能被处理，这可能导致性能问题。

**不确定性**：请求可能不会被任何处理器处理，这需要在设计时考虑如何处理这种情况。

**调试困难**：由于请求处理链的动态性，调试可能比较困难。



## 建造者模式（Builder Pattern）



建造者模式（Builder Pattern）是一种创建型设计模式，它允许你在构建复杂对象时，可以分步骤地创建对象，并且可以改变其内部表示。建造者模式通常用于当创建对象的算法应该独立于该对象的组成部分以及它们的装配方式时。

### 代码示例：

#### 定义产品类

首先，定义一个产品类，它将由建造者创建。

```java
// 产品类
public class Product {
    private String partA;
    private String partB;
    private String partC;

    // 省略getter和setter方法

    @Override
    public String toString() {
        return "Product{" +
                "partA='" + partA + '\'' +
                ", partB='" + partB + '\'' +
                ", partC='" + partC + '\'' +
                '}';
    }
}

```

#### 定义建造者接口

定义一个建造者接口，声明创建产品各个部分的方法。

```java
// 建造者接口
public interface Builder {
    void buildPartA(String partA);
    void buildPartB(String partB);
    void buildPartC(String partC);
    Product getResult();
}

```

#### 实现具体的建造者

实现建造者接口，具体化创建产品各个部分的逻辑。

```
// 具体建造者
public class ConcreteBuilder implements Builder {
    private Product product = new Product();

    @Override
    public void buildPartA(String partA) {
        product.setPartA(partA);
    }

    @Override
    public void buildPartB(String partB) {
        product.setPartB(partB);
    }

    @Override
    public void buildPartC(String partC) {
        product.setPartC(partC);
    }

    @Override
    public Product getResult() {
        return product;
    }
}

```

#### 定义指导者

定义一个指导者类，它使用建造者接口来构建产品。

```java
// 指导者
public class Director {
    private Builder builder;

    public Director(Builder builder) {
        this.builder = builder;
    }

    public Product construct(String partA, String partB, String partC) {
        builder.buildPartA(partA);
        builder.buildPartB(partB);
        builder.buildPartC(partC);
        return builder.getResult();
    }
}

```

#### 使用建造者模式

最后，在客户端代码中使用指导者和具体建造者来创建产品。

```java
public class BuilderPatternDemo {
    public static void main(String[] args) {
        Builder builder = new ConcreteBuilder();
        Director director = new Director(builder);

        Product product = director.construct("PartA", "PartB", "PartC");
        System.out.println(product);
    }
}

```

在上述代码中，Product 是最终要创建的产品对象。Builder 是建造者接口，ConcreteBuilder 是实现了建造者接口的具体建造者类。Director 类负责使用建造者来构建产品。客户端代码通过指导者来构建产品，而不需要直接与具体建造者交互。



### 优缺点

##### 优点

1. **封装性好**：建造者模式将复杂对象的构建过程与其表示分离，客户端不需要知道产品内部的构建细节
2. **构建过程灵活**：通过不同的建造者实现，可以创建不同表示的对象，即使是在同一个构建过程中
3. **减少代码冗余**：当对象的构建过程相似时，可以使用相同的建造者类，减少重复代码
4. **易于扩展**：增加新的具体建造者类不会影响现有的代码结构，符合开闭原则
5. **提高代码的可读性和可维护性**：建造者模式将构建过程分解为多个步骤，使得构建过程更加清晰，易于理解和维护。

##### 缺点

1. **增加了类的数量**：建造者模式需要定义多个类（包括产品类、抽象建造者类和具体建造者类），这可能会增加系统的复杂性。

2. **客户端需要知道具体的建造者**：虽然客户端不需要知道产品的构建细节，但客户端仍然需要选择合适的建造者来创建对象。

3. **不适用于简单对象**：对于简单的对象，使用建造者模式可能会显得过于复杂，增加不必要的开销。

4. **可能导致性能问题**：如果构建过程非常复杂，建造者模式可能会导致性能问题，因为需要创建多个对象和调用多个方法。

5. **不适用于需要参数化构建过程的场景**：如果构建过程需要根据不同的参数进行不同的处理，建造者模式可能不是最佳选择，因为它通常需要为每种参数组合定义一个新的建造者类。

##### 总结

   建造者模式适用于构建过程复杂、需要分步骤创建对象且对象的表示可能变化的场景。它能够提高代码的可读性和可维护性，但也可能增加系统的复杂性和类的数量。在选择使用建造者模式时，需要权衡其优缺点，确保它适合当前的项目需求。

## 策略模式（Strategy Pattern）

`策略模式（Strategy Pattern）`是一种行为设计模式，它允许在运行时选择算法的行为。策略模式定义了一系列算法，并将每个算法封装在独立的类中，使得它们可以互换。这样可以避免大量的条件判断，并且使得算法的变化独立于使用算法的客户。

### 策略模式的主要组成部分

**策略接口**：定义了一个算法族的公共接口。
**具体策略类**：实现了策略接口，提供具体的算法实现。
**上下文类**：使用策略接口的一个实例来调用策略，上下文类持有一个策略对象的引用，可以在运行时切换不同的策略。

### 代码示例

#### 定义策略接口

```java
public interface Strategy {
    void execute();
}

```

#### 实现具体策略类

```java
public class ConcreteStrategyA implements Strategy {
    @Override
    public void execute() {
        System.out.println("Executing strategy A");
    }
}

public class ConcreteStrategyB implements Strategy {
    @Override
    public void execute() {
        System.out.println("Executing strategy B");
    }
}

```

#### 定义上下文类

```java
public class Context {
    private Strategy strategy;

    public void setStrategy(Strategy strategy) {
        this.strategy = strategy;
    }

    public void executeStrategy() {
        if (strategy != null) {
            strategy.execute();
        }
    }
}

```

#### 使用策略模式

```java
public class StrategyPatternDemo {
    public static void main(String[] args) {
        Context context = new Context();

        // 使用策略A
        context.setStrategy(new ConcreteStrategyA());
        context.executeStrategy();

        // 切换到策略B
        context.setStrategy(new ConcreteStrategyB());
        context.executeStrategy();
    }
}

```

在上述代码中，`Strategy` 是策略接口，`ConcreteStrategyA`和 `ConcreteStrategyB` 是具体策略类，`Context` 是上下文类，它持有一个策略对象的引用，并可以在运行时切换不同的策略。

通过这种方式，`策略模式`使得算法的变化独立于使用算法的客户，并且可以避免大量的条件判断语句，使得代码更加清晰和易于维护。

### 优缺点

#### 优点

**算法独立**：策略模式使得算法的变化独立于使用算法的客户。
**避免条件判断**：通过使用策略模式，可以避免大量的条件判断语句。
**易于扩展**：增加新的策略类不会影响现有的代码结构，符合开闭原则。

#### 缺点

**客户端需要知道所有策略**：客户端需要知道所有的策略类，并决定使用哪一个策略。
**增加了类的数量**：每一种策略都需要一个具体的策略类，可能会增加系统的复杂性。

# 设计模式比较



## 建造者模式与工厂模式



`建造者模式（Builder Pattern）`和`工厂模式（Factory Pattern）`都属于创建型设计模式，它们都用于对象的创建，但是它们之间存在一些关键的区别



### 区别



#### 目的

`工厂模式`：主要用于创建对象，而不关心对象的具体构建过程。客户端只需要知道工厂类，就可以得到所需的对象实例。

`建造者模式`：不仅用于创建对象，还关注对象内部的构建过程。它允许逐步构建复杂对象，并且可以改变其内部表示。

#### 创建对象的方式

`工厂模式`：通常通过一个静态方法或一个工厂类来创建对象。客户端调用工厂方法时，不需要知道对象的具体构建过程。

`建造者模式`：通过一个指导者（Director）和一个或多个具体建造者（Concrete Builder）来构建对象。客户端通过指导者来构建对象，而不需要直接与具体建造者交互。

#### 适用场景

`工厂模式`：适用于创建简单对象，或者当对象的创建过程不需要复杂配置时。

`建造者模式`：适用于创建复杂对象，尤其是当对象的构建过程需要多个步骤，或者对象的表示可能变化时。

#### 对象的复杂性

`工厂模式`：通常用于创建简单的对象，对象的构建过程相对简单，不需要多个步骤。

`建造者模式`：用于创建复杂的对象，对象的构建过程可能涉及多个步骤和组件。

### 总结

**工厂模式**：关注对象的创建，不关心对象的构建过程，适用于简单对象的创建。

**建造者模式**：关注对象的构建过程，适用于复杂对象的创建，可以灵活地构建对象的内部表示。

在实际应用中，可以根据具体的需求选择合适的模式。如果对象的创建过程简单，可以使用工厂模式；如果对象的构建过程复杂，可以使用建造者模式。



## 策略模式和责任链模式

`策略模式`和`责任链模式`都是行为设计模式，它们都用于处理算法或请求的逻辑，但是它们的目的和使用场景有所不同。

### 区别

#### 目的

**策略模式**：定义了一系列算法，并将每个算法封装在独立的类中，使得它们可以互换。策略模式的主要目的是允许在运行时选择算法的行为。

**责任链模式**：定义了一个处理请求的对象链，请求沿着链传递，直到有一个对象处理它为止。责任链模式的主要目的是解耦发送者和接收者，使得多个对象都有机会处理请求。

#### 结构

**策略模式**：通常包含一个上下文类，该类持有一个策略接口的引用，以及多个实现了策略接口的具体策略类。

**责任链模式**：包含一个处理器接口，多个实现了该接口的具体处理器类，以及一个用于组装处理器链的机制。

#### 使用场景

**策略模式**：适用于需要在运行时选择不同算法或行为的场景，例如支付方式的选择、排序算法的选择等。

**责任链模式**：适用于请求的处理者不是固定的，或者需要动态地指定处理者的场景，例如日志记录、权限验证、请求过滤等。

#### 灵活性

**策略模式**：客户端可以选择具体的策略，策略的改变不会影响到客户端代码。

**责任链模式**：可以在运行时动态地添加或删除处理器，改变处理器的顺序，或者改变处理器的处理逻辑。

#### 性能

**策略模式**：通常性能开销较小，因为策略的选择是在编译时确定的。

**责任链模式**：可能会有性能开销，因为请求需要沿着链传递，直到找到合适的处理器。

### 总结

**策略模式**：适用于需要在运行时选择不同算法或行为的场景，客户端可以选择具体的策略。

**责任链模式**：适用于请求的处理者不是固定的，或者需要动态地指定处理者的场景，请求沿着链传递，直到找到合适的处理器。

在实际应用中，可以根据具体的需求选择合适的模式。如果需要在运行时选择不同的算法或行为，可以使用策略模式；如果需要动态地处理请求，并且处理者不是固定的，可以使用责任链模式。
