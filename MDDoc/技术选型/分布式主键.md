# 分布式主键id

在分布式系统中，设计数据库表的主键是一个关键问题。传统的自增主键（如 MySQL 的 `AUTO_INCREMENT`）在分布式环境下无法保证全局唯一性，因此需要采用分布式主键设计方案。以下是几种常见的分布式主键设计方案及其优缺点：

------

## 1. **UUID**

UUID（Universally Unique Identifier）是一个 128 位的全局唯一标识符，通常以 32 位十六进制字符串表示。

### 实现方式：

- 使用编程语言或数据库内置的 UUID 生成函数（如 Java 的 `UUID.randomUUID()` 或 MySQL 的 `UUID()`）。

### 优点：

- **全局唯一**：几乎可以保证在分布式环境下的唯一性。
- **无需中心化服务**：每个节点可以独立生成 UUID。

### 缺点：

- **存储空间大**：UUID 是 128 位，占用 16 字节，比自增主键大。
- **无序性**：UUID 是无序的，可能导致索引碎片化，影响查询性能。
- **可读性差**：UUID 是长字符串，不易于人类阅读和调试。

### 适用场景：

- 对存储空间和性能要求不高的场景。
- 需要简单、快速实现全局唯一 ID 的场景。

------

## 2. **Snowflake 算法**

Snowflake 是 Twitter 开源的分布式 ID 生成算法，生成一个 64 位的长整型 ID。

### ID 结构：

- **1 位符号位**：固定为 0。
- **41 位时间戳**：表示毫秒级时间，可以使用约 69 年。
- **10 位机器 ID**：表示分布式系统中的机器节点，最多支持 1024 个节点。
- **12 位序列号**：表示同一毫秒内生成的 ID 序号，最多支持 4096 个 ID。

### 实现方式：

- 每个节点独立生成 ID，通过时间戳、机器 ID 和序列号保证唯一性。

### 优点：

- **高性能**：本地生成，无需网络调用。
- **有序性**：ID 按时间递增，适合作为索引。
- **存储空间小**：64 位长整型，占用 8 字节。

### 缺点：

- **依赖系统时钟**：如果系统时钟回拨，可能导致 ID 重复。
- **机器 ID 需要分配**：需要确保每个节点的机器 ID 唯一。

### 适用场景：

- 高并发、高性能的分布式系统。
- 需要有序 ID 的场景。

### springboot示例

在 Spring Boot 中实现 Snowflake 算法生成分布式唯一 ID 是一个常见的需求。Snowflake 算法是 Twitter 开源的一种分布式 ID 生成算法，生成的 ID 是一个 64 位的长整型，结构如下：

- **1 位符号位**：固定为 0。
- **41 位时间戳**：表示毫秒级时间，可以使用约 69 年。
- **10 位机器 ID**：表示分布式系统中的机器节点，最多支持 1024 个节点。
- **12 位序列号**：表示同一毫秒内生成的 ID 序号，最多支持 4096 个 ID。

以下是 Spring Boot 实现 Snowflake 算法的详细步骤：

------

#### 1. **创建 Snowflake ID 生成器类**

首先，创建一个 `SnowflakeIdGenerator` 类来实现 Snowflake 算法。





```
import java.util.concurrent.atomic.AtomicLong;

public class SnowflakeIdGenerator {

    // 起始时间戳（2023-01-01）
    private static final long START_TIMESTAMP = 1672531200000L;

    // 机器 ID 位数
    private static final long WORKER_ID_BITS = 10L;

    // 序列号位数
    private static final long SEQUENCE_BITS = 12L;

    // 最大机器 ID（1023）
    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);

    // 最大序列号（4095）
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);

    // 机器 ID 左移位数
    private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;

    // 时间戳左移位数
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;

    // 机器 ID
    private final long workerId;

    // 序列号
    private final AtomicLong sequence = new AtomicLong(0);

    // 上次生成 ID 的时间戳
    private long lastTimestamp = -1L;

    /**
     * 构造函数
     *
     * @param workerId 机器 ID
     */
    public SnowflakeIdGenerator(long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException("Worker ID must be between 0 and " + MAX_WORKER_ID);
        }
        this.workerId = workerId;
    }

    /**
     * 生成下一个 ID
     */
    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();

        // 如果当前时间小于上次生成 ID 的时间，说明系统时钟回拨
        if (currentTimestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards. Refusing to generate ID.");
        }

        // 如果是同一毫秒内生成的 ID，递增序列号
        if (currentTimestamp == lastTimestamp) {
            long sequenceVal = sequence.incrementAndGet() & MAX_SEQUENCE;
            // 如果序列号超出范围，等待下一毫秒
            if (sequenceVal == 0) {
                currentTimestamp = waitNextMillis(currentTimestamp);
            }
        } else {
            // 如果不是同一毫秒，重置序列号
            sequence.set(0);
        }

        lastTimestamp = currentTimestamp;

        // 生成 ID
        return ((currentTimestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence.get();
    }

    /**
     * 等待下一毫秒
     */
    private long waitNextMillis(long currentTimestamp) {
        long nextTimestamp = System.currentTimeMillis();
        while (nextTimestamp <= currentTimestamp) {
            nextTimestamp = System.currentTimeMillis();
        }
        return nextTimestamp;
    }
}
```

## 3. **数据库分段（Segment）**

通过数据库表生成分段 ID，每个节点从数据库中获取一段 ID 范围。

### 实现方式：

1. 创建一个数据库表用于存储 ID 段：

   

   

   ```
   CREATE TABLE id_segment (
       biz_tag VARCHAR(128) PRIMARY KEY,  -- 业务标识
       max_id BIGINT NOT NULL,            -- 当前最大 ID
       step INT NOT NULL,                 -- 步长
       version BIGINT NOT NULL            -- 版本号（用于乐观锁）
   );
   ```

2. 每个节点从数据库中获取一段 ID 范围：

   - 查询当前 `max_id` 和 `step`。
   - 更新 `max_id = max_id + step`。
   - 使用 `max_id` 到 `max_id + step` 的范围作为本地缓存。

### 优点：

- **简单易实现**：基于数据库，无需额外组件。
- **可控性强**：可以通过调整步长控制 ID 生成速度。

### 缺点：

- **依赖数据库**：数据库可能成为性能瓶颈。
- **ID 不连续**：每个节点获取的 ID 范围是独立的，可能导致 ID 不连续。

### 适用场景：

- 中小型分布式系统。
- 对 ID 连续性要求不高的场景。

#### 3. **实现 ID 生成器**

创建一个 `SegmentIdGenerator` 类来管理 ID 段的获取和分配。

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class SegmentIdGenerator {

    @Autowired
    private IdSegmentRepository idSegmentRepository;

    // 本地缓存
    private long currentId = 0;
    private long maxId = 0;

    /**
     * 获取下一个 ID
     *
     * @param bizTag 业务标识
     * @return 下一个 ID
     */
    @Transactional
    public synchronized long nextId(String bizTag) {
        // 如果本地缓存用尽，从数据库获取新的 ID 段
        if (currentId >= maxId) {
            fetchSegmentFromDb(bizTag);
        }
        return currentId++;
    }

    /**
     * 从数据库获取新的 ID 段
     */
    private void fetchSegmentFromDb(String bizTag) {
        IdSegment idSegment = idSegmentRepository.findById(bizTag)
                .orElseThrow(() -> new RuntimeException("Biz tag not found: " + bizTag));

        // 计算新的 maxId
        long newMaxId = idSegment.getMaxId() + idSegment.getStep();

        // 更新数据库
        idSegment.setMaxId(newMaxId);
        idSegment.setVersion(idSegment.getVersion() + 1);
        idSegmentRepository.save(idSegment);

        // 更新本地缓存
        currentId = idSegment.getMaxId() - idSegment.getStep();
        maxId = newMaxId;
    }
}
```

## 4. **Redis 自增**

利用 Redis 的单线程特性，通过 `INCR` 或 `INCRBY` 命令生成全局唯一 ID。

### 实现方式：

1. 使用 Redis 的 `INCR` 命令生成自增 ID：

   ```
   INCR global_id
   ```

2. 如果需要分段，可以为每个业务设置不同的 key：

   ```
   INCR biz_tag:id
   ```

### 优点：

- **高性能**：Redis 是内存数据库，性能高。
- **简单易用**：基于 Redis 的命令，实现简单。

### 缺点：

- **依赖 Redis**：Redis 可能成为单点故障。
- **ID 连续性依赖 Redis 持久化**：如果 Redis 宕机且未持久化，可能导致 ID 重复。

### 适用场景：

- 需要高性能 ID 生成的场景。
- 已经使用 Redis 作为基础设施的系统。

## 5. **ZooKeeper 顺序节点**

利用 ZooKeeper 的顺序节点特性生成全局唯一 ID。

### 实现方式：

1. 在 ZooKeeper 中创建一个持久化节点（如 `/id_generator`）。
2. 在每个节点下创建顺序临时节点（如 `/id_generator/node_`）。
3. 顺序节点的序号即为全局唯一 ID。

### 优点：

- **强一致性**：ZooKeeper 保证全局一致性。
- **高可用**：ZooKeeper 是分布式协调服务，具有高可用性。

### 缺点：

- **性能较低**：ZooKeeper 的写性能较低，不适合高并发场景。
- **复杂性高**：需要维护 ZooKeeper 集群。

### 适用场景：

- 对一致性要求极高的场景。
- 已经使用 ZooKeeper 作为基础设施的系统。

## 6. **Leaf 算法**

Leaf 是美团开源的分布式 ID 生成服务，结合了 Snowflake 和数据库分段的优点。

### 实现方式：

1. 使用 Snowflake 算法生成 ID。
2. 使用数据库分段作为容错机制，当 Snowflake 不可用时，回退到数据库分段。

### 优点：

- **高性能**：优先使用 Snowflake 算法。
- **高可用**：支持数据库分段作为容错机制。

### 缺点：

- **复杂性高**：需要实现 Snowflake 和数据库分段的结合。

### 适用场景：

- 高并发、高可用的分布式系统。

```java
        // 如果是同一毫秒内生成的 ID，递增序列号
        if (currentTimestamp == lastTimestamp) {
            long sequenceVal = sequence.incrementAndGet() & MAX_SEQUENCE;
            // 如果序列号超出范围，等待下一毫秒
            if (sequenceVal == 0) {
                currentTimestamp = waitNextMillis(currentTimestamp);
            }
        } else {
            // 如果不是同一毫秒，重置序列号
            sequence.set(0);
        }

        lastTimestamp = currentTimestamp;

        // 生成 ID
        return ((currentTimestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence.get();
    }

    private long waitNextMillis(long currentTimestamp) {
        long nextTimestamp = System.currentTimeMillis();
        while (nextTimestamp <= currentTimestamp) {
            nextTimestamp = System.currentTimeMillis();
        }
        return nextTimestamp;
    }
}
```

##### 数据库分段部分：

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class SegmentIdGenerator {

    @Autowired
    private LeafAllocRepository leafAllocRepository;

    // 本地缓存
    private long currentId = 0;
    private long maxId = 0;

    /**
     * 获取下一个 ID
     *
     * @param bizTag 业务标识
     * @return 下一个 ID
     */
    @Transactional
    public synchronized long nextId(String bizTag) {
        // 如果本地缓存用尽，从数据库获取新的 ID 段
        if (currentId >= maxId) {
            fetchSegmentFromDb(bizTag);
        }
        return currentId++;
    }

    /**
     * 从数据库获取新的 ID 段
     */
    private void fetchSegmentFromDb(String bizTag) {
        LeafAlloc leafAlloc = leafAllocRepository.findById(bizTag)
                .orElseThrow(() -> new RuntimeException("Biz tag not found: " + bizTag));

        // 计算新的 maxId
        long newMaxId = leafAlloc.getMaxId() + leafAlloc.getStep();

        // 更新数据库
        leafAlloc.setMaxId(newMaxId);
        leafAlloc.setUpdateTime(LocalDateTime.now());
        leafAllocRepository.save(leafAlloc);

        // 更新本地缓存
        currentId = leafAlloc.getMaxId() - leafAlloc.getStep();
        maxId = newMaxId;
    }
}
```

##### 结合 Snowflake 和数据库分段：

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;

@Component
public class LeafIdGenerator {

    @Autowired
    private SnowflakeIdGenerator snowflakeIdGenerator;

    @Autowired
    private SegmentIdGenerator segmentIdGenerator;

    @Value("${leaf.biz-tag}")
    private String bizTag;

    /**
     * 获取下一个 ID
     */
    public long nextId() {
        try {
            // 优先使用 Snowflake 算法
            return snowflakeIdGenerator.nextId();
        } catch (Exception e) {
            // 如果 Snowflake 不可用，回退到数据库分段
            return segmentIdGenerator.nextId(bizTag);
        }
    }
}
```

#### 7. **总结**

通过实现 Leaf 算法，可以在 Spring Boot 中生成高性能、高可用的分布式唯一 ID。Leaf 算法的核心思想是：

- **优先使用 Snowflake 算法**：生成高性能、有序的 ID。
- **数据库分段作为容错机制**：当 Snowflake 不可用时，回退到数据库分段生成 ID。

在实际应用中，可以根据需求调整机器 ID 的分配方式和数据库分段的步长，确保系统的稳定性和可靠性。

## 7. **总结**

以下是各种分布式主键设计方案的对比：

| 方案       | 优点                 | 缺点                            | 适用场景           |
| :--------- | :------------------- | :------------------------------ | :----------------- |
| UUID       | 全局唯一，简单易用   | 存储空间大，无序性              | 简单场景           |
| Snowflake  | 高性能，有序性       | 依赖系统时钟，机器 ID 分配      | 高并发场景         |
| 数据库分段 | 简单易实现，可控性强 | 依赖数据库，ID 不连续           | 中小型系统         |
| Redis 自增 | 高性能，简单易用     | 依赖 Redis，ID 连续性依赖持久化 | 高性能场景         |
| ZooKeeper  | 强一致性，高可用     | 性能较低，复杂性高              | 强一致性场景       |
| Leaf       | 高性能，高可用       | 复杂性高                        | 高并发、高可用场景 |

根据实际需求选择合适的分布式主键设计方案，确保系统的性能和可靠性。
