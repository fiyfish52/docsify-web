# 分布式主键id

在分布式系统中，设计数据库表的主键是一个关键问题。传统的自增主键（如 MySQL 的 `AUTO_INCREMENT`）在分布式环境下无法保证全局唯一性，因此需要采用分布式主键设计方案。以下是几种常见的分布式主键设计方案及其优缺点：

------

## 1. **UUID**

UUID（Universally Unique Identifier）是一个 128 位的全局唯一标识符，通常以 32 位十六进制字符串表示。

### 实现方式：

- 使用编程语言或数据库内置的 UUID 生成函数（如 Java 的 `UUID.randomUUID()` 或 MySQL 的 `UUID()`）。

### 优点：

- **全局唯一**：几乎可以保证在分布式环境下的唯一性。
- **无需中心化服务**：每个节点可以独立生成 UUID。

### 缺点：

- **存储空间大**：UUID 是 128 位，占用 16 字节，比自增主键大。
- **无序性**：UUID 是无序的，可能导致索引碎片化，影响查询性能。
- **可读性差**：UUID 是长字符串，不易于人类阅读和调试。

### 适用场景：

- 对存储空间和性能要求不高的场景。
- 需要简单、快速实现全局唯一 ID 的场景。

### 各个版本区别

#### UUID 各版本区别及使用场景详解

UUID (Universally Unique Identifier) 是用于标识信息的128位数字，标准形式为32个十六进制数字，分为5段，格式为8-4-4-4-12共36个字符。以下是各版本UUID的区别及其适用场景。

##### 一、UUID版本概述

| 版本 | 名称               | 生成方式                        | 特点                 |
| ---- | ------------------ | ------------------------------- | -------------------- |
| v1   | 基于时间和MAC地址  | 时间戳 + MAC地址                | 可追溯生成时间和机器 |
| v2   | DCE安全UUID        | 时间戳 + MAC地址 + 本地域标识符 | 极少使用             |
| v3   | 基于MD5哈希        | 命名空间 + 名称的MD5哈希        | 确定性生成           |
| v4   | 随机UUID           | 随机数生成                      | 完全随机             |
| v5   | 基于SHA-1哈希      | 命名空间 + 名称的SHA-1哈希      | 确定性生成           |
| v6   | 改进的时间排序UUID | 类似v1但时间字段排序优化        | 更适合数据库索引     |
| v7   | 时间排序UUID       | 时间戳 + 随机数                 | 时间可排序           |
| v8   | 自定义UUID         | 自由定义                        | 特殊用途             |

##### 二、各版本详细说明

###### 1. UUID v1：基于时间和MAC地址

**生成原理**：
- 60位时间戳（UTC时间从1582-10-15 00:00:00开始的100纳秒间隔数）
- 48位MAC地址
- 14位序列号（防止同一MAC地址在同一时间戳生成重复UUID）

**格式示例**：
```
xxxxxxxx-xxxx-1xxx-xxxx-xxxxxxxxxxxx
```

**优点**：
- 可以追踪生成时间和生成机器
- 在局域网内保证唯一性

**缺点**：
- 暴露MAC地址可能带来隐私问题
- 时间戳高位在前，不适合直接作为数据库主键（导致索引碎片）

**使用场景**：
- 需要追踪生成来源的分布式系统
- 传统系统兼容需求

###### 2. UUID v2：DCE安全UUID

**特点**：
- 与v1类似，但用本地域标识符替代部分时间戳
- 极少在实际中使用
- 多数UUID库不实现此版本

###### 3. UUID v3：基于MD5哈希的命名空间UUID

**生成原理**：
- 需要提供命名空间UUID和一个名称
- 对`命名空间UUID + 名称`进行MD5哈希
- 替换版本号为3

**格式示例**：
```
xxxxxxxx-xxxx-3xxx-xxxx-xxxxxxxxxxxx
```

**优点**：
- 确定性：相同输入总是生成相同UUID
- 不暴露机器信息

**缺点**：
- 使用MD5算法（虽然在此场景无安全问题）
- 哈希冲突概率高于v5

**使用场景**：
- 需要从固定名称生成固定UUID的场景
- 兼容性要求高于安全性的场景

**示例（Java）**：
```java
UUID namespace = UUID.fromString("6ba7b810-9dad-11d1-80b4-00c04fd430c8");
UUID uuid = UUID.nameUUIDFromBytes(("myapp" + "mydata").getBytes());
```

###### 4. UUID v4：随机UUID

**生成原理**：
- 122位完全随机数
- 固定版本号为4

**格式示例**：
```
xxxxxxxx-xxxx-4xxx-xxxx-xxxxxxxxxxxx
```

**优点**：
- 生成简单快速
- 不包含任何敏感信息
- 足够随机，冲突概率极低

**缺点**：
- 完全无序，不适合作为数据库主键（导致索引碎片）
- 无法从中获取任何生成信息

**使用场景**：
- 需要简单唯一标识符的大多数场景
- 临时标识符
- 不关心排序的分布式ID

**示例（Java）**：
```java
UUID uuid = UUID.randomUUID(); // 默认生成v4
```

###### 5. UUID v5：基于SHA-1哈希的命名空间UUID

**生成原理**：
- 类似v3，但使用SHA-1算法替代MD5
- 替换版本号为5

**格式示例**：
```
xxxxxxxx-xxxx-5xxx-xxxx-xxxxxxxxxxxx
```

**优点**：
- 确定性生成
- 使用更安全的SHA-1算法
- 比v3哈希冲突概率更低

**缺点**：
- 计算比v3稍慢

**使用场景**：
- 需要从固定名称生成固定UUID的安全敏感场景
- 分布式系统中需要一致生成相同UUID

**示例（Python）**：
```python
import uuid
namespace = uuid.NAMESPACE_URL
uuid.uuid5(namespace, 'https://example.com')
```

###### 6. UUID v6：改进的时间排序UUID

**生成原理**：
- 类似v1的时间+MAC地址结构
- 但重新排列时间字段使其更适合作为数据库主键

**优点**：
- 保留v1的可追溯性
- 时间字段排序优化，更适合作为数据库索引

**使用场景**：
- 需要时间顺序且可追溯的数据库主键
- 替代v1的新系统

###### 7. UUID v7：时间排序UUID

**生成原理**：
- 48位Unix时间戳（毫秒精度）
- 74位随机数
- 比v6更简单的时间排序实现

**优点**：
- 时间戳在前，索引效率高
- 不暴露机器信息
- 比v1/v6更简单的实现

**使用场景**：
- 需要时间顺序的分布式ID
- 数据库主键的理想选择

###### 8. UUID v8：自定义UUID

**特点**：
- 无固定结构
- 保留UUID格式但允许自定义内容
- 用于特殊用途或实验

##### 三、各版本使用场景推荐

| 场景               | 推荐版本 | 理由                     |
| ------------------ | -------- | ------------------------ |
| 通用唯一标识       | v4       | 简单随机，满足大多数需求 |
| 需要确定性的命名ID | v5       | 安全哈希，可重复生成     |
| 数据库主键         | v7       | 时间排序，索引友好       |
| 需要追溯生成时间   | v1/v6    | 包含时间戳信息           |
| 分布式系统节点ID   | v1       | 包含机器信息             |
| 兼容旧系统         | v1/v4    | 广泛支持                 |
| 安全敏感命名ID     | v5       | 使用SHA-1更安全          |

```java
// v3

// v1 (需要第三方库如com.fasterxml.uuid:java-uuid-generator)

```

###### Python

##### 五、性能考虑

1. **生成速度**：
   - v4最快（纯随机）
   - v1/v6需要获取时间戳和机器信息
   - v3/v5需要计算哈希

2. **存储效率**：
   - 所有版本都是128位(16字节)
   - 某些数据库有优化的UUID存储类型

3. **索引效率**：
   - v7/v6/v1等时间排序版本更适合作为索引
   - v4随机性会导致索引碎片

##### 六、安全考虑

1. **信息泄露**：
   - v1/v6可能泄露MAC地址和时间信息
   - v4/v5不会泄露任何信息

2. **预测风险**：
   - v1可能被预测（如果知道大概生成时间）
   - v4完全随机，无法预测

##### 七、总结建议

1. **默认选择v4**：大多数应用场景足够，简单高效
2. **数据库主键用v7**：时间排序，索引友好（如PostgreSQL 14+原生支持）
3. **确定性需求用v5**：需要从名称生成固定UUID时
4. **避免v1**：除非确实需要MAC地址和时间信息
5. **新项目考虑v7**：结合了时间排序和隐私保护的优势

UUID版本选择应基于具体需求：是否需要确定性、时间排序、隐私保护等特性。现代应用越来越倾向于使用v4或v7版本。

## 2. **Snowflake 算法**

Snowflake 是 Twitter 开源的分布式 ID 生成算法，生成一个 64 位的长整型 ID。

### ID 结构：

- **1 位符号位**：固定为 0。
- **41 位时间戳**：表示毫秒级时间，可以使用约 69 年。
- **10 位机器 ID**：表示分布式系统中的机器节点，最多支持 1024 个节点。
- **12 位序列号**：表示同一毫秒内生成的 ID 序号，最多支持 4096 个 ID。

### 实现方式：

- 每个节点独立生成 ID，通过时间戳、机器 ID 和序列号保证唯一性。

### 优点：

- **高性能**：本地生成，无需网络调用。
- **有序性**：ID 按时间递增，适合作为索引。
- **存储空间小**：64 位长整型，占用 8 字节。

### 缺点：

- **依赖系统时钟**：如果系统时钟回拨，可能导致 ID 重复。
- **机器 ID 需要分配**：需要确保每个节点的机器 ID 唯一。

### 适用场景：

- 高并发、高性能的分布式系统。
- 需要有序 ID 的场景。

### springboot示例

在 Spring Boot 中实现 Snowflake 算法生成分布式唯一 ID 是一个常见的需求。Snowflake 算法是 Twitter 开源的一种分布式 ID 生成算法，生成的 ID 是一个 64 位的长整型，结构如下：

- **1 位符号位**：固定为 0。
- **41 位时间戳**：表示毫秒级时间，可以使用约 69 年。
- **10 位机器 ID**：表示分布式系统中的机器节点，最多支持 1024 个节点。
- **12 位序列号**：表示同一毫秒内生成的 ID 序号，最多支持 4096 个 ID。

#### 1. **创建 Snowflake ID 生成器类**

首先，创建一个 `SnowflakeIdGenerator` 类来实现 Snowflake 算法。



##### 方案一：

```java
import java.util.concurrent.atomic.AtomicLong;

public class SnowflakeIdGenerator {

    // 起始时间戳（2023-01-01）
    private static final long START_TIMESTAMP = 1672531200000L;

    // 机器 ID 位数
    private static final long WORKER_ID_BITS = 10L;

    // 序列号位数
    private static final long SEQUENCE_BITS = 12L;

    // 最大机器 ID（1023）
    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);

    // 最大序列号（4095）
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);

    // 机器 ID 左移位数
    private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;

    // 时间戳左移位数
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;

    // 机器 ID
    private final long workerId;

    // 序列号
    private final AtomicLong sequence = new AtomicLong(0);

    // 上次生成 ID 的时间戳
    private long lastTimestamp = -1L;

    /**
     * 构造函数
     *
     * @param workerId 机器 ID
     */
    public SnowflakeIdGenerator(long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException("Worker ID must be between 0 and " + MAX_WORKER_ID);
        }
        this.workerId = workerId;
    }

    /**
     * 生成下一个 ID
     */
    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();

        // 如果当前时间小于上次生成 ID 的时间，说明系统时钟回拨
        if (currentTimestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards. Refusing to generate ID.");
        }

        // 如果是同一毫秒内生成的 ID，递增序列号
        if (currentTimestamp == lastTimestamp) {
            long sequenceVal = sequence.incrementAndGet() & MAX_SEQUENCE;
            // 如果序列号超出范围，等待下一毫秒
            if (sequenceVal == 0) {
                currentTimestamp = waitNextMillis(currentTimestamp);
            }
        } else {
            // 如果不是同一毫秒，重置序列号
            sequence.set(0);
        }

        lastTimestamp = currentTimestamp;

        // 生成 ID
        return ((currentTimestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence.get();
    }

    /**
     * 等待下一毫秒
     */
    private long waitNextMillis(long currentTimestamp) {
        long nextTimestamp = System.currentTimeMillis();
        while (nextTimestamp <= currentTimestamp) {
            nextTimestamp = System.currentTimeMillis();
        }
        return nextTimestamp;
    }
}
```

##### 方案二

```java
public class SnowflakeIdWorker {
    // 起始时间戳（2020-01-01）
    private final long twepoch = 1577808000000L;

    // 机器ID所占位数
    private final long workerIdBits = 5L;
    // 数据中心ID所占位数
    private final long datacenterIdBits = 5L;
    // 序列号所占位数
    private final long sequenceBits = 12L;

    // 最大机器ID
    private final long maxWorkerId = ~(-1L << workerIdBits);
    // 最大数据中心ID
    private final long maxDatacenterId = ~(-1L << datacenterIdBits);

    // 机器ID左移位数
    private final long workerIdShift = sequenceBits;
    // 数据中心ID左移位数
    private final long datacenterIdShift = sequenceBits + workerIdBits;
    // 时间戳左移位数
    private final long timestampLeftShift = sequenceBits + workerIdBits + datacenterIdBits;

    // 序列号掩码
    private final long sequenceMask = ~(-1L << sequenceBits);

    private long workerId;
    private long datacenterId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdWorker(long workerId, long datacenterId) {
        if (workerId > maxWorkerId || workerId < 0) {
            throw new IllegalArgumentException(String.format("worker Id can't be greater than %d or less than 0", maxWorkerId));
        }
        if (datacenterId > maxDatacenterId || datacenterId < 0) {
            throw new IllegalArgumentException(String.format("datacenter Id can't be greater than %d or less than 0", maxDatacenterId));
        }
        this.workerId = workerId;
        this.datacenterId = datacenterId;
    }

    public synchronized long nextId() {
        long timestamp = timeGen();

        // 如果当前时间小于上一次ID生成的时间戳，说明系统时钟回退过
        if (timestamp < lastTimestamp) {
            throw new RuntimeException(
                    String.format("Clock moved backwards. Refusing to generate id for %d milliseconds", lastTimestamp - timestamp));
        }

        // 如果是同一时间生成的，则进行序列号自增
        if (lastTimestamp == timestamp) {
            sequence = (sequence + 1) & sequenceMask;
            // 序列号溢出
            if (sequence == 0) {
                // 阻塞到下一毫秒，获得新的时间戳
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            // 时间戳改变，序列号重置
            sequence = 0L;
        }

        lastTimestamp = timestamp;

        // 组装ID
        return ((timestamp - twepoch) << timestampLeftShift)
                | (datacenterId << datacenterIdShift)
                | (workerId << workerIdShift)
                | sequence;
    }

    protected long tilNextMillis(long lastTimestamp) {
        long timestamp = timeGen();
        while (timestamp <= lastTimestamp) {
            timestamp = timeGen();
        }
        return timestamp;
    }

    protected long timeGen() {
        return System.currentTimeMillis();
    }
}

```

#### 2. **配置机器 ID**

在分布式系统中，每个节点需要有一个唯一的机器 ID。可以通过配置文件或环境变量指定机器 ID。

##### 在 `application.yml` 中配置机器 ID：

yaml



```
snowflake:
  worker-id: 1
```

##### 读取配置并初始化 `SnowflakeIdGenerator`：





```
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class SnowflakeConfig {

    @Value("${snowflake.worker-id}")
    private long workerId;

    @Bean
    public SnowflakeIdGenerator snowflakeIdGenerator() {
        return new SnowflakeIdGenerator(workerId);
    }
}
```

#### 3. **使用 Snowflake ID 生成器**

在 Spring Boot 应用中，可以通过注入 `SnowflakeIdGenerator` 来生成分布式唯一 ID。

##### 示例：在 Service 中使用





```
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service
public class SnowflakeService {

    @Autowired
    private SnowflakeIdGenerator snowflakeIdGenerator;

    public long generateId() {
        return snowflakeIdGenerator.nextId();
    }
}
```

#### 5. **注意事项**

1. **机器 ID 分配**：
   - 确保每个节点的机器 ID 唯一。
   - 可以通过配置文件、环境变量或分布式配置中心（如 ZooKeeper、Consul）动态分配机器 ID。
2. **时钟回拨问题**：
   - 如果系统时钟回拨，可能导致 ID 重复。
   - 可以通过 NTP 同步系统时钟，或在代码中处理时钟回拨异常。
3. **性能优化**：
   - Snowflake 算法是本地生成 ID，性能非常高。
   - 如果需要更高的性能，可以将 `SnowflakeIdGenerator` 设计为无锁模式。

#### 6. **总结**

通过实现 Snowflake 算法，可以在 Spring Boot 中生成高性能、全局唯一的分布式 ID。Snowflake 算法的核心思想是通过时间戳、机器 ID 和序列号组合生成 ID，具有以下优点：

- **高性能**：本地生成，无需网络调用。
- **有序性**：ID 按时间递增，适合作为索引。
- **存储空间小**：64 位长整型，占用 8 字节。

在实际应用中，可以根据需求调整机器 ID 的分配方式和时钟回拨的处理策略，确保系统的稳定性和可靠性。

## 3. **数据库分段（Segment）**

通过数据库表生成分段 ID，每个节点从数据库中获取一段 ID 范围。

### 实现方式：

1. 创建一个数据库表用于存储 ID 段：

   

   

   ```
   CREATE TABLE id_segment (
       biz_tag VARCHAR(128) PRIMARY KEY,  -- 业务标识
       max_id BIGINT NOT NULL,            -- 当前最大 ID
       step INT NOT NULL,                 -- 步长
       version BIGINT NOT NULL            -- 版本号（用于乐观锁）
   );
   ```

2. 每个节点从数据库中获取一段 ID 范围：

   - 查询当前 `max_id` 和 `step`。
   - 更新 `max_id = max_id + step`。
   - 使用 `max_id` 到 `max_id + step` 的范围作为本地缓存。

### 优点：

- **简单易实现**：基于数据库，无需额外组件。
- **可控性强**：可以通过调整步长控制 ID 生成速度。

### 缺点：

- **ID 不连续**：每个节点获取的 ID 范围是独立的，可能导致 ID 不连续。

- 中小型分布式系统。
- 对 ID 连续性要求不高的场景。

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
public class SegmentIdGenerator {

    @Autowired
    private IdSegmentRepository idSegmentRepository;

    // 本地缓存
    private long currentId = 0;
    private long maxId = 0;

    /**
     * 获取下一个 ID
     *
     * @param bizTag 业务标识
     * @return 下一个 ID
     */
    @Transactional
    public synchronized long nextId(String bizTag) {
        // 如果本地缓存用尽，从数据库获取新的 ID 段
        if (currentId >= maxId) {
            fetchSegmentFromDb(bizTag);
        }
        return currentId++;
    }

    /**
     * 从数据库获取新的 ID 段
     */
    private void fetchSegmentFromDb(String bizTag) {
        IdSegment idSegment = idSegmentRepository.findById(bizTag)
                .orElseThrow(() -> new RuntimeException("Biz tag not found: " + bizTag));

        // 计算新的 maxId
        long newMaxId = idSegment.getMaxId() + idSegment.getStep();

        // 更新数据库
        idSegment.setMaxId(newMaxId);
        idSegment.setVersion(idSegment.getVersion() + 1);
        idSegmentRepository.save(idSegment);

        // 更新本地缓存
        currentId = idSegment.getMaxId() - idSegment.getStep();
        maxId = newMaxId;
    }
}
```

## 4. **Redis 自增**

利用 Redis 的单线程特性，通过 `INCR` 或 `INCRBY` 命令生成全局唯一 ID。

### 实现方式：

1. 使用 Redis 的 `INCR` 命令生成自增 ID：

   ```

   ```

2. 如果需要分段，可以为每个业务设置不同的 key：

   ```
   INCR biz_tag:id
   ```

### 优点：

- **高性能**：Redis 是内存数据库，性能高。
- **简单易用**：基于 Redis 的命令，实现简单。

### 缺点：

- **依赖 Redis**：Redis 可能成为单点故障。
- **ID 连续性依赖 Redis 持久化**：如果 Redis 宕机且未持久化，可能导致 ID 重复。

### 适用场景：

- 需要高性能 ID 生成的场景。
- 已经使用 Redis 作为基础设施的系统。

## 5. **ZooKeeper 顺序节点**

利用 ZooKeeper 的顺序节点特性生成全局唯一 ID。

### 实现方式：

1. 在 ZooKeeper 中创建一个持久化节点（如 `/id_generator`）。
2. 在每个节点下创建顺序临时节点（如 `/id_generator/node_`）。
3. 顺序节点的序号即为全局唯一 ID。

### 优点：

- **强一致性**：ZooKeeper 保证全局一致性。
- **高可用**：ZooKeeper 是分布式协调服务，具有高可用性。

### 缺点：

- **性能较低**：ZooKeeper 的写性能较低，不适合高并发场景。
- **复杂性高**：需要维护 ZooKeeper 集群。

### 适用场景：

- 对一致性要求极高的场景。
- 已经使用 ZooKeeper 作为基础设施的系统。

## 6. **Leaf 算法**

Leaf 是美团开源的分布式 ID 生成服务，结合了 Snowflake 和数据库分段的优点。

### 实现方式：

1. 使用 Snowflake 算法生成 ID。
2. 使用数据库分段作为容错机制，当 Snowflake 不可用时，回退到数据库分段。

### 优点：

- **高性能**：优先使用 Snowflake 算法。
- **高可用**：支持数据库分段作为容错机制。

### 缺点：

- **复杂性高**：需要实现 Snowflake 和数据库分段的结合。

### 适用场景：

- 高并发、高可用的分布式系统。

##### Snowflake 部分：

```java
public class SnowflakeIdGenerator {

    private static final long START_TIMESTAMP = 1672531200000L; // 起始时间戳（2023-01-01）
    private static final long WORKER_ID_BITS = 10L;            // 机器 ID 位数
    private static final long SEQUENCE_BITS = 12L;             // 序列号位数
    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS); // 最大机器 ID
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);   // 最大序列号
    private static final long WORKER_ID_SHIFT = SEQUENCE_BITS;          // 机器 ID 左移位数
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS; // 时间戳左移位数

    private final long workerId;  // 机器 ID
    private final AtomicLong sequence = new AtomicLong(0); // 序列号
    private long lastTimestamp = -1L; // 上次生成 ID 的时间戳

    public SnowflakeIdGenerator(long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER_ID) {
            throw new IllegalArgumentException("Worker ID must be between 0 and " + MAX_WORKER_ID);
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();

        // 如果当前时间小于上次生成 ID 的时间，说明系统时钟回拨
        if (currentTimestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards. Refusing to generate ID.");
        }

        // 如果是同一毫秒内生成的 ID，递增序列号
        if (currentTimestamp == lastTimestamp) {
            long sequenceVal = sequence.incrementAndGet() & MAX_SEQUENCE;
            // 如果序列号超出范围，等待下一毫秒
            if (sequenceVal == 0) {
                currentTimestamp = waitNextMillis(currentTimestamp);
            }
        } else {
            // 如果不是同一毫秒，重置序列号
            sequence.set(0);
        }

        lastTimestamp = currentTimestamp;

        // 生成 ID
        return ((currentTimestamp - START_TIMESTAMP) << TIMESTAMP_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence.get();
    }

    private long waitNextMillis(long currentTimestamp) {
        long nextTimestamp = System.currentTimeMillis();
        while (nextTimestamp <= currentTimestamp) {
            nextTimestamp = System.currentTimeMillis();
        }
        return nextTimestamp;
    }
}
```
